# 产品说明（PRODUCT）

这份文档回答工程文档不回答的问题：**这是给谁做的、解决什么场景、为什么这样设计、
以及还没做什么。**

## 一、使用场景

**用户**：投放优化师 / 增长运营 / 商业化产品经理——每天要看账户、每周要复盘、
预算调整前需要依据的人。

**当前替代方案与痛点**：

| 现状 | 痛点 |
|---|---|
| 投放后台看板 | 只看得到总量，看不出「哪些计划在拖后腿」；维度固定，不能按自己的问题拆 |
| 人工拉数 + Excel | 口径靠记忆，同一个指标不同人算出不同数；小样本的比率差被当成结论 |
| 交给 AI 写一段总结 | 读起来很专业，但数字可能不是报表里的；没人能复现它是怎么得出结论的 |
| 优化师凭经验 | 有效但不可传递；换个人接手就断档 |

**本产品的定位**：把「投放复盘」这件事从**经验驱动**变成**可复核的规则 + 可验证的结论**。

## 二、一条命令的输入输出

```bash
python -m adops run --source csv --data-file 我的投放导出.csv --out outputs/本周
```

产出 `outputs/本周/report.md`，结构固定为九节：

| 节 | 内容 | 对应用户的问题 |
|---|---|---|
| 0 | 结论摘要 | 「所以到底要做什么？」 |
| 1 | 核心指标 + 漏斗 + 计费口径自检 | 「整体怎么样？」 |
| 2 | 数据质量体检 | 「这份数据能信吗？」 |
| 3 | 计划效率（含量化判定） | 「哪些计划该动？」 |
| 4 | 分时洞察 | 「什么时候加价？」 |
| 5 | 诊断发现（证据 → 动作 → 影响面） | 「为什么、怎么改？」 |
| 6 | 预算再分配建议 | 「钱往哪挪？」 |
| 7 | 下一轮实验设计 | 「怎么验证？」 |
| 9 | 口径附录 + 复核 SQL | 「你凭什么这么说？」 |

**每一节都回答一个真实会被问到的问题**——这是本产品与「AI 写一段总结」的核心差别。

## 三、关键设计决策与理由

### 1. 为什么用规则做诊断，而不是让模型直接判断？

| 维度 | 规则 | 模型直接判断 |
|---|---|---|
| 可复算 | 同输入同输出 | 每次措辞与侧重都不同 |
| 可反驳 | 能指出「你的门槛是 30 次点击，我的计划只有 28 次」 | 只能反驳「我觉得」 |
| 可回归 | 改一条阈值能看到哪些结论变了 | 无法 diff |
| 交付速度 | 快（脚本跑批） | 慢且不稳定 |

结论：**决策交给规则，表达交给模型**。这不是「不用 AI」，而是把 AI 放在它真正有优势的
位置——把结构化结论写成运营看得懂的话，且写完还能被校验。

### 2. 为什么给 AI 输出加「数字回指守卫」？

因为模型最危险的失败不是写得差，而是**写出一个报表里没有的数**。
人工审核也常漏掉这种错误——数字看起来都很合理。所以把纪律做成代码：模型输出的每个数字
要么能在证据表里匹配到（容差 5%，容忍四舍五入），要么整段作废、回落到确定性模板。

这条守卫在 CI 里是一条会失败的检查（`scripts/check_narrative.py`）。

### 3. 为什么所有阈值都要求「样本量达标」才报警？

误报的代价不对称：**漏报一次机会的成本，远小于让运营对报表失去信任。**
所以宁可漏报——转化数不到 10 的计划不做效率判定，曝光不到 1 000 的计划不做 CTR 判定，
3 个计划时不算 HHI，24 个小时的时段机会做 Bonferroni 校正。

这个取舍写在 `docs/DIAGNOSIS-RULES.md` 的「不报的情形」一节里，与规则本身同等重要。

### 4. 为什么报告要附「复核用 SQL」？

业务方在动预算之前，往往要在数仓里自己核一遍。能顺手给出与结论口径完全一致的 SQL，
是「可复核」最实际的落地方式——否则复核成本高，最终大家还是凭感觉改预算。
6 段 SQL 覆盖计划效率、分时效率、数据质量自查、日趋势、归因覆盖率、实验读数。

### 5. 为什么数据质量单独作为一道闸，且分级？

投放复盘最常见的翻车不是结论算错，而是**输入本身有问题**（重复导出、回传漏了一半）。
所以质量体检在指标之前，并且分三级：

- `fail` = 确定性数据错误（缺失/重复/逻辑冲突）→ 结论不可用，先修数据；
- `warn` = 需要人工确认的口径问题（如归因覆盖率偏低）→ 结论可用但有风险；
- 业务层面的发现（归因口径）交给诊断层出结论，避免同一件事报两次、还把报告判死。

### 6. 为什么把「未识别的列」「钳位了多少行」打印出来？

清洗层会静默修正一些东西（点击 > 曝光时钳位、负消耗置空）。**修正必须留痕**，
否则用户会以为数据本来是干净的。审计信息进报告第 2 节。

## 四、验收标准（怎么判断这份报告有用）

| 标准 | 检验方式 |
|---|---|
| 数字可复算 | 从 `outputs/*/clean/` 加总能推出报告里的 KPI（有测试） |
| 结论可复现 | 两次运行除生成时间外逐字节一致（有测试） |
| 口径唯一 | 报告、SQL、测试三处口径一致；附恒等式自检 |
| 不误导 | 公开数据的绝对水平、消耗单位、时间口径都印在报告里 |
| 不越权 | 输出的是「先试哪个方向 + 假设 + 观察期」，不是「照此执行能省 X 元」 |
| 零依赖可跑 | 无 API key、无外网也能出报告 |

## 五、迭代记录（真实数据驱动的两次修正）

这两条是这份产品最值得讲的迭代，因为它们都是**被真实数据推翻的初始设计**：

1. **消耗异常检测：按明细行 → 按日汇总。**
   初始实现按每条曝光做 IQR 异常检测，在真实数据上 7.09% 的记录被标为异常——
   而它们完全正常：单次曝光的价格由竞价瞬时决定，天然是离散长尾分布。
   修正后把检测对象改成日消耗汇总（时间口径异常才是真信号），误报降到 0。

2. **去重键：排除 user_id → 包含全部列。**
   初始实现认为「同一用户可能多次看到同一广告」，于是把 `user_id` 排除在去重键之外，
   结果 2.76% 的记录被误判为重复，整份数据被判成「不可用」。
   修正：`user_id` 不同的两条曝光就是两次真实曝光，去重必须覆盖全部列。

两次修正都留下了测试（`tests/test_quality.py`、`tests/test_normalize.py`）与代码注释，
避免以后被改回去。

## 六、还没做（明确的边界）

| 未做 | 原因 / 替代方案 |
|---|---|
| 多触点归因建模（Shapley / 马尔可夫） | 需要用户级转化路径数据，本产品只有曝光级日志；当前只做归因覆盖率体检 |
| 边际效率曲线 / 预算响应模型 | 需要实验数据积累；当前用一阶线性近似，并把假设打印给用户 |
| 实时出价 / 在线学习 | 批式复盘与实时竞价是两套系统，本产品只做前者 |
| 素材内容分析（图像/文本） | 属于创意侧工具，与投放数据诊断边界不同 |
| 多账户汇总视图 | 当前一账户一次运行；多账户可在流程编排层解决，不必进核心 |

## 七、可用性观察（产品向）

报告是 Markdown，可直接进知识库、发群、贴周报；图表是 PNG，可直接进 PPT。
所有中间产物是 CSV/JSON，可被别的工具消费。
**没有前端**是刻意的取舍：投放优化师已经在浏览器里开着投放后台，
再开一个后台的边际收益低于「让结论直接进他们已有的工作流」（文档、周报、群）。
